## 2. 需求分析

### 目标用户

- **管理员**：维护商品（增删改查、上架/下架、库存管理）、管理全部订单（状态流转、取消）、查看数据统计看板；
- **普通用户**：浏览上架商品、加入购物车并下单、查看自己的订单、取消待支付订单。

### 核心功能点

1. 用户注册 / 登录（bcrypt 密码加密、JWT 无状态鉴权）；
2. RBAC 权限控制（`admin` / `user` 双角色，前端路由守卫 + 后端中间件双重校验）；
3. 商品管理：分页列表、关键词/分类筛选、CRUD、上架/下架、低库存提示；
4. 订单管理：下单（事务扣库存、防超卖）、订单状态机流转（待支付→已支付→已发货→已完成）、取消订单回滚库存、商品快照；
5. 数据统计看板：总销售额、订单数、用户数、商品数、分类占比、近 7 天销售趋势（ECharts 可视化）。

### 非功能性需求

- **性能**：数据库连接池（connectionLimit=10）；列表接口分页限制（pageSize ≤ 100）；核心接口索引覆盖；
- **安全**：密码 bcrypt 哈希存储；JWT 过期校验；管理员接口 403 拦截；统一错误响应不泄露堆栈；删除被引用商品被外键约束拒绝；
- **兼容性**：前端响应式布局；接口统一 JSON 格式，前后端通过 `code=0` 约定解耦。

## 3. 数据库设计

5 张核心表：`users`（用户）、`products`（商品）、`orders`（订单）、`order_items`（订单明细，含商品快照）、`addresses`（收货地址簿）。

设计要点：

- 订单明细保存**商品名称与单价快照**，商品后续改价/改名不影响历史订单；
- `products.stock` 加 `CHECK (stock >= 0)` 约束；
- 外键：`orders.user_id → users.id`，`order_items.order_id → orders.id (ON DELETE CASCADE)`，`addresses.user_id → users.id (ON DELETE CASCADE)`；
- 订单表除状态流转外，还记录发货信息 `express_company` / `express_no` / `shipped_at`、订单备注 `remark`、归档标记 `is_archived`（归档后列表隐藏、数据保留可追溯）；
- 收货地址簿 `addresses` 与用户一对多，单用户地址上限 20 条、仅一条默认地址；下单时收货人 / 电话 / 地址仍以快照写入 `orders`，地址簿后续修改不影响历史订单；
- 索引：`username` 唯一索引、`orders(user_id)`、`orders(status)`、`orders(is_archived)`、`orders(status, created_at)`、`addresses(user_id)`、`products(status/category)`。

完整 ER 图与表结构详见《数据库设计文档.md》，建库脚本见 `docs/database.sql`。

## 5. 核心功能实现说明（难点/亮点）

### 5.1 订单创建：事务 + 条件更新防超卖

下单涉及多张表的写操作（扣库存、写订单、写明细），必须保证原子性。实现上：

1. 使用连接池 `getConnection()` 开启事务；
2. 查询商品时加 `FOR UPDATE` 行锁，防止并发下单读到脏库存；
3. 扣库存使用**条件更新**：`UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`，`affectedRows === 0` 即库存不足，抛出异常回滚；
4. 任一步骤失败统一 `rollback()`，`finally` 中 `release()` 归还连接。

关键代码（`backend/src/controllers/order.controller.js`）：

```js
const conn = await pool.getConnection();
try {
  await conn.beginTransaction();
  // ... 校验商品、收集快照、计算总金额
  const [upd] = await conn.query(
    'UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?',
    [s.quantity, s.productId, s.quantity]
  );
  if (upd.affectedRows === 0) throw Object.assign(new Error(`商品「${s.name}」库存不足`), { status: 400 });
  // ... 写 orders、order_items
  await conn.commit();
} catch (err) {
  await conn.rollback();
  throw err;
} finally {
  conn.release();
}
```

### 5.2 RBAC 权限：后端中间件 + 前端路由守卫双重校验

- **后端**：`authRequired` 中间件解析 `Authorization: Bearer <token>`，校验通过后挂载 `req.user = { id, username, role }`；`adminRequired` 在其后校验角色，非管理员直接返回 403。商品管理、全部订单、统计接口统一挂这两个中间件；
- **前端**：`router.beforeEach` 根据 Pinia 中的角色判断页面 `meta.roles` 是否放行；axios 请求拦截器自动附加 token，响应拦截器对 401 统一清除登录态并跳转登录页。

### 5.3 订单状态机

状态只允许按 `pending → paid → shipped → completed` 顺序流转（`cancelled` 仅由取消操作产生），后端在事务中校验：

```js
const flow = { pending: 0, paid: 1, shipped: 2, completed: 3, cancelled: -1 };
if (flow[status] !== flow[order.status] + 1) {
  throw Object.assign(new Error(`订单状态不允许从 ${order.status} 流转到 ${status}`), { status: 400 });
}
```

### 5.4 收货地址簿与订单超时自动取消

**收货地址簿**：独立设计 `addresses` 表（而非直接在用户表存地址字段），支持一个用户维护多条地址、并保证「同一用户仅一条默认地址」。接口层在「设为默认」时先执行 `UPDATE addresses SET is_default = 0 WHERE user_id = ?` 再置一，避免出现两条默认地址；同时限制单用户最多 20 条地址、手机号必须匹配 11 位格式，防止恶意刷数据。下单时地址簿只作为选择来源，收货人 / 电话 / 地址仍以快照写入 `orders`，保证历史订单不受地址后续修改影响。

**订单超时自动取消**：待支付订单若不处理会长期占用库存，因此新增 `services/orderExpireService.js`（业务逻辑）与 `services/orderExpireTask.js`（调度）两层：服务启动 5 秒后先扫描一次，之后每 60 秒扫描一次，把超过 30 分钟仍未支付的 `pending` 订单置为 `cancelled`，并在同一事务内回滚库存。

关键代码（`backend/src/services/orderExpireTask.js`）：

```js
// 启动后延迟 5 秒执行一次，避开服务刚启动时的初始化压力
firstRunTimer = setTimeout(runOnce, 5000);
if (firstRunTimer.unref) firstRunTimer.unref();
timer = setInterval(runOnce, intervalMs);
```

> 两个定时器都调用 `unref()`，不阻塞进程退出；`runOnce()` 内部 try/catch，单次执行异常不会导致任务中断。

## 7. 遇到的问题与解决方案

### 问题 1：删除已被订单引用的商品会触发外键报错

- **现象**：对已产生订单的商品调用删除接口，后端抛出 `ER_ROW_IS_REFERENCED_2`（外键约束拒绝）。
- **排查过程**：先以为是 SQL 语法问题，检查后确认语法正确；随后查看错误码，发现是 `order_items.product_id` 外键约束在拦截删除。
- **解决方案**：在删除接口捕获外键错误，明确提示"该商品已被订单引用，无法删除，建议改为下架"，引导用户使用下架功能替代物理删除——既保护历史订单数据完整性，又改善了前端操作体验。

### 问题 2：并发下单可能超卖（库存扣成负数）

- **现象**：设计初稿直接在事务里 `SELECT stock` 判断后 `UPDATE stock = stock - ?`，两个并发请求可能同时读到剩余 1 件库存而都下单成功，最终库存变为 -1，且 `CHECK(stock>=0)` 会让数据库直接报错。
- **排查过程**：代码走查发现"先读后写"存在竞态窗口；单纯加 `CHECK` 约束只能把问题变成报错，不能保证业务成功。
- **解决方案**：改为**条件更新** `UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?`，用受影响行数判断是否扣减成功，并配合 `SELECT ... FOR UPDATE` 行锁与事务回滚，从根上杜绝超卖。

### 问题 3：前端 401 处理不当会造成跳转风暴

- **现象**：初版响应拦截器在遇到 401 时直接 `router.push('/login')`，但多个并发请求同时 401 时，会连续触发多次跳转和重复弹窗，甚至与登录页路由守卫互相干扰。
- **排查过程**：观察浏览器控制台，发现多个接口同时失败时日志重复打印、页面出现"登录→跳转→登录"循环。
- **解决方案**：统一收敛到用户 store 的 `logout()`（幂等清除 localStorage），只提示一次并跳转一次；同时在 axios 拦截器集中处理，避免各页面重复编写 401 逻辑。

## 8. 总结与反思

- 完整走通了"需求分析 → 数据库设计 → 后端 API → 前端页面 → 联调 → 部署"的全栈开发流程，理解了前后端分离模式下数据流转与接口约定（统一响应格式、错误码）的重要性；

- 认识到"数据库约束是最后一道防线"——业务层要先保证正确性，约束负责兜底。
