## 二、collection 改造清单（7 项）

| # | 问题 | 改造做法 |
|---|---|---|
| 1 | 原集合靠手工复制 token，换机即废 | 登录脚本自动 `pm.collectionVariables.set('token' / 'userToken')`，双角色变量贯穿全集合 |
| 2 | 注册固定用户名，第二次跑必报「用户名已存在」 | 前置脚本生成 `stu+时间戳` 随机用户名 → `{{randUser}}` |
| 3 | 商品/地址/订单 id 全部写死 `1`，库里没 id=1 就 404 | 全部改为动态：`{{productId}}` 由「挑选可下单商品」自动取，`{{newProductId}}`/`{{addressId}}`/`{{orderId}}`/`{{orderId2}}` 由响应写入 |
| 4 | 用 admin token 跑「支付/确认收货/取消用户订单」→ 全 403 | 订单本人动线改用 `{{userToken}}`，admin 只负责发货、归档、超时检查，正好演示 RBAC 边界 |
| 5 | 改密码后不回改，账号被改死，下轮跑不了 | 增加「修改密码（改回）」请求，`admin123 → Admin@1234 → admin123` 闭环，**数据零残留** |
| 6 | 零断言 | 每个请求 2 条起步断言（HTTP 状态 + 业务码 code=0），关键请求追加业务断言（token 是字符串、订单号存在、存在可下单商品） |
| 7 | 只有正向用例，红色不可辨 | 新增「负向用例」分组，明确断言 4xx 拦截语义，让「红色」变成可验收的预期结果 |

**接口覆盖增补**：商品分类、我的订单、全部订单、订单详情、取消订单、取消归档、低库存等原集合未覆盖的接口已补齐。

## 四、改造前 11 条红色定性（含金量说明）

| 请求 | 返回 | 真相 |
|---|---|---|
| `DELETE /products/1` | 400 | 商品被订单引用，接口拒绝并建议改为下架 —— **保护逻辑正确** |
| `POST /orders` | 400 | 用的商品「无线机械键盘」已下架 —— 用例数据问题 |
| `POST /orders/1/pay`、`/confirm` | 403 | admin token 操作 user 的订单 —— **越权拦截正确** |
| `POST /orders/1/cancel` | 400 | 非待支付状态不可取消 —— **状态机正确** |
| `POST /orders/1/status` | 400 | shipped → shipped 跳级非法 —— **状态机正确** |
| `POST /orders/1/archive` | 400 | 仅已完成/已取消可归档 —— **状态机正确** |
| `POST /orders/1/unarchive` | 400 | 未归档无需取消归档 —— **状态机正确** |
| `PUT /addresses/1`、`POST /addresses/1/default`、`DELETE /addresses/1` | 404 | 真实地址 id 是 30/31/32，无 id=1 —— 用例写死 id |

**结论：接口业务逻辑全对，11 条红色全部来自用例设计缺陷。** 它们现在被重构为「负向用例」分组，作为**验收亮点**保留——老师看到的是「我主动验证了非法请求确实被拦住」。

## 五、后续建议

### P0（答辩前务必做）

1. **一键重置脚本** `npm run db:reset`：`DROP + CREATE + 建表 + 灌种子 + 建 admin/user` 一条命令还原演示环境。现场演示前跑一次，避免历史脏数据干扰。
2. **启动前置检查**：脚本先 `sc query MySQL80` 确认服务 Running，再启 node；否则页面报「网络异常」而误判为代码坏了。
3. **改动后必须重启 node**：新增路由后旧进程仍加载旧代码，前端会报「接口不存在」，排查时先看进程版本，别只盯源码。

### P1（提升交付质量）

4. **接进 CI**：GitHub Actions 里 `npm ci → mysql service → npm run seed → newman run`，出 `htmlextra` HTML 报告附在仓库 README，比截图有说服力。
5. **弱口令治理**：`admin123 / user123 / 123456` 仅适合本地演示，README 明确标注「仅演示环境」；真实部署改强口令并通过环境变量注入。
6. **环境分离**：再加一份 `local` / `prod` 环境文件，用 `--environment` 切换，避免误跑线上。

### P2（技术深度加分）

7. **断言深化**：库存扣减前后对比、下单后 `GET /orders/:id` 回查金额一致、重复支付必须 400（幂等性）、分页边界 `pageSize=0 / 999`。
8. **状态机全矩阵用例**：把 5 条合法流转 + 全部非法跳级做成数据驱动用例（newman `--iteration-data` CSV），答辩可现场展示「20 条非法流转 100% 拦截」。
9. **超时任务可观测**：`orderExpireTask` 建议加执行日志表，`POST /orders/expire-check` 手动触发时能查到「本次取消了几单、回滚了多少库存」。
