## 三、业务闭环实测（不是分接口，是连起来跑）

```
新建商品(库存100) → 加地址 → 用地址簿下单 2 件 → 库存 100→98
   → 超库存下单被拒（"库存不足"）
   → 支付 pending→paid → 重复支付被拒
   → 管理员发货 paid→shipped（顺丰 SF1234567890，记录发货时间）
   → 已发货状态尝试取消被拒（状态机拦截）
   → 用户确认收货 shipped→completed
   → 归档 → 归档列表可查到 → 取消归档
   → 另起一单验证取消：库存 98→95→98（精确回滚）
```

这一条链路走完，说明订单域的状态机、库存、权限、事务四件事都是通的，不是各自孤立的空壳接口。

## 四、安全与数据校验覆盖情况

| 检查项 | 实现方式 | 实测结果 |
| --- | --- | --- |
| 密码明文泄露 | bcrypt 哈希入库 | 数据库无明文 |
| 未登录访问 | `authRequired` 中间件 | 返回 401 |
| 普通用户越权 | `adminRequired` 中间件 | 统计/商品增删改/订单管理均 403 |
| 跨用户访问他人数据 | SQL 强制带 `user_id` 条件 | 返回 404 / 403，查不到数据 |
| SQL 注入 | 全参数化查询 + 排序白名单 | 无字符串拼接 |
| 超卖 | 事务 + `FOR UPDATE` 行锁 + `stock >= ?` 条件更新 | 双层拦截 |
| 前端篡改金额 | 价格一律后端按 productId 重查 | 前端只传商品 ID 与数量 |
| 收货信息篡改 | addressId 后端回查回填 | 前端传的收货人信息被覆盖 |
| 数据快照 | order_items 存商品名与单价快照 | 商品改价不影响历史订单 |

## 六、功能边界说明（答辩被问"为什么没做"时用）

以下是常见电商功能，本项目**未实现**，属于课程实训范围外的合理裁剪，答辩时应主动交代而不是被问出来：

| 未做功能 | 原因口径 |
| --- | --- |
| 真实支付渠道（微信/支付宝） | 涉及商户资质与资金安全，实训用模拟支付的状态流转替代，重点是状态机与事务，不是渠道对接 |
| 商品评价 / 评分 | 属于 UGC 系统，工作量独立，与订单主链路正交 |
| 优惠券 / 满减 | 涉及价格计算引擎，会把下单金额逻辑复杂化，实训阶段刻意不引入 |
| 多规格 SKU（颜色/尺码） | 需要 sku 表拆分，商品模型会复杂一倍，本项目用单规格保清晰 |
| 收藏 / 浏览足迹 | 弱业务，不影响主链路 |
| 退款 / 售后 | 只做了取消订单回滚库存，退款流程涉及资金反向流转，未涉及 |
| 图片上传 | 商品图用 URL 字段，避免引入文件存储与 OSS 配置 |
| 订单导出 Excel | 看板已能看数据，导出属于附加需求 |

**答辩话术**：不是做不了，是在"闭环完整"和"每个模块都讲得清"之间做了取舍——我把订单域做深（事务、行锁、状态机、库存回滚），把非核心业务做浅，保证演示时每个点都能讲透。
