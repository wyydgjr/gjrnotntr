> 用途：答辩时左边开工程版、右边开极简版，同一个功能用两种写法对照讲。

## 三、十个核心知识点，双版本对照讲

极简版文件内已用注释分节，答辩时按"第 N 节"直接定位。

### 知识点 1：统一响应结构（极简版第 2 节）

```js
// 极简版：3 行搞定
const ok = (res, data = null, message = 'success') => res.json({ code: 0, message, data });
const fail = (res, status, message) => res.status(status).json({ code: status, message, data: null });
```

```js
// 工程版：单独的 utils/response.js
exports.success = (res, data, message = 'success') => res.status(200).json({ code: 0, message, data });
exports.error = (res, status, message) => res.status(status).json({ code: status, message, data: null });
```

**为什么要有统一结构**：前端 `request.js` 只写一次拦截器，判断 `code !== 0` 就弹错误，所有接口通用。如果每个接口返回格式不一样，前端每调一个接口都得写一套判断。

**答辩话术**：`code=0` 表示成功，失败时 `code` 等于 HTTP 状态码——这样前端既能靠 HTTP 状态码做全局拦截，也能靠 `code` 做业务判断，两边都不冲突。

### 知识点 2：统一异常兜底（极简版第 2 节 `wrap`）

```js
const wrap = (fn) => (req, res) => fn(req, res).catch((e) => {
  fail(res, e.status || 500, e.status ? e.message : '服务器内部错误');
});
const bad = (status, message) => Object.assign(new Error(message), { status });

// 用法
app.get('/api/products/:id', auth, wrap(async (req, res) => {
  if (!rows.length) throw bad(404, '商品不存在');   // 抛出来就行，不用每处写 res.json
}));
```

工程版对应 `middlewares\asyncHandler.js` + `middlewares\errorHandler.js`，思路一样但拆成两个文件。

**解决什么问题**：Express 4 不会自动捕获 async 函数里的异常，一旦 `await` 抛错，请求就挂住不返回，前端一直转圈。所以要么每个接口包 try/catch（37 个接口 = 37 个 try/catch），要么用 `wrap` 统一包一层。极简版选了后者，**一行代码解决 37 处重复**。

**答辩话术**：这是我认为工程化里最值得讲的一点——抽象不是为了显得高级，是为了消灭重复。37 个接口如果各写一遍 try/catch，改一次错误格式就得改 37 个地方。

### 知识点 3：JWT 无状态鉴权（极简版第 2 节 `auth`）

```js
function auth(req, res, next) {
  const h = req.headers.authorization || '';
  const token = h.startsWith('Bearer ') ? h.slice(7) : '';
  if (!token) return fail(res, 401, '未登录，请先登录');
  try { req.user = jwt.verify(token, SECRET); next(); }   // 解出 { id, username, role }
  catch (e) { fail(res, 401, '登录已过期或无效，请重新登录'); }
}
```

签发：

```js
const token = jwt.sign({ id, username, role }, SECRET, { expiresIn: '2d' });
```

**三个必答追问**：

| 追问 | 回答 |
| --- | --- |
| Token 存哪？ | 前端存 localStorage，每次请求放进 `Authorization: Bearer xxx` 请求头 |
| 为什么不用 Session？ | Session 要在服务端存一份、还要考虑多机共享（要么粘性会话要么 Redis）。JWT 自带签名，服务端不存状态，`verify` 一下就信任，横向扩容无压力。代价是**签发后无法主动作废**——所以改密码后要让旧 Token 失效的话，得加黑名单或版本号，本项目实训阶段没做，属于已知取舍。 |
| 密钥能硬编码吗？ | 极简版为了演示写死 `'simple_secret'`，工程版从 `.env` 读 `JWT_SECRET`。生产环境必须走环境变量，而且不能是这种弱密钥。 |

**答辩话术（能加分）**：JWT 的载荷是 Base64 编码、不是加密，任何人拿到都能解出里面的 id 和 role。所以它只能用来证明"这张票是我签的"，绝不能往里放敏感信息——这是很多人踩的坑。

### 知识点 4：RBAC 权限控制（极简版第 2 节 `adminOnly`）

```js
function adminOnly(req, res, next) {
  if (req.user.role !== 'admin') return fail(res, 403, '无权限访问，需要管理员账号');
  next();
}
// 用法：只要在路由上挂两个中间件，先验身份再验权限
app.post('/api/products', auth, adminOnly, wrap(async (req, res) => { ... }));
```

**答辩话术**：权限是"中间件链"实现的：`auth` 负责"你是谁"，`adminOnly` 负责"你能不能干"。这两个是独立的，所以能自由组合——商品增删改要 `auth + adminOnly`，商品列表只要 `auth`（普通用户也能看，但只看在售的）。

**追问：普通用户能看到已下架商品吗？** 不能。极简版列表里有一行：

```js
if (!isAdmin) { where.push('p.status = ?'); params.push('on'); }   // 普通用户只看在售
```

这就是**数据级权限**，不只是接口级权限——同一个接口，管理员能看到全部，普通用户被强制加上过滤条件。

### 知识点 5：密码存储（极简版第 3 节）

```js
const hash = bcrypt.hashSync(password, 10);        // 10 = 加盐轮数
if (!bcrypt.compareSync(password, user.password)) return fail(res, 401, '用户名或密码错误');
```

**三个必答追问**：

| 追问 | 回答 |
| --- | --- |
| 为什么不能存明文？ | 数据库一旦泄露，用户所有网站的账号都危险（很多人密码复用）。 |
| 为什么不存 MD5？ | MD5 太快了，显卡每秒能算几十亿次，弱密码瞬间被彩虹表反查出来。bcrypt 故意设计得慢，轮数 10 意味着单次校验约几十毫秒——对登录来说无感，对暴力破解来说是灾难。 |
| 为什么登录失败提示"用户名或密码错误"，而不是"用户不存在"？ | 防止**用户名枚举**。如果分开提示，攻击者就能靠提示差异把系统里有哪些账号全试出来。 |

**细节（能体现你读过文档）**：bcrypt 每次哈希都会自动生成不同的随机盐并混进结果字符串里，所以同一个密码两次哈希结果不同，但 `compareSync` 都能校验通过——盐不用单独存一列。

### 知识点 6：连接池（极简版第 1 节）

```js
const db = mysql.createPool({
  host: '127.0.0.1', user: 'root', password: '123456', database: 'ecommerce',
  connectionLimit: 10, charset: 'utf8mb4', dateStrings: true,
});
```

**必答追问：为什么要用连接池？**
建立一条 MySQL 连接要 TCP 三次握手 + 身份认证，耗时几十毫秒。如果每个请求都新建一条，并发一上来数据库直接被连接数打满。池子就是预先建好 10 条常驻连接，用完还回去，请求来了直接取。

**`dateStrings: true` 是干嘛的**：mysql2 默认把 DATETIME 转成 JS Date 对象，转 JSON 时会变成带时区的 ISO 字符串，前端显示还要再转一次。加了这个参数直接返回 `"2026-11-09 15:34:10"` 字符串，前端拿来就能显示，省掉一整套时区坑。

**答辩话术**：`connectionLimit: 10` 不是越大越好。连接是要吃数据库内存的，10 已经能撑住这个体量的并发了，调到 200 反而可能把 MySQL 拖死。

### 知识点 7：事务下单（极简版第 6 节 `POST /api/orders`）★★核心

```js
const conn = await db.getConnection();
try {
  await conn.beginTransaction();      // ① 开启事务

  // ② 校验每个商品并加行锁（FOR UPDATE）
  for (const it of items) {
    const [rows] = await conn.query('SELECT ... FROM products WHERE id = ? FOR UPDATE', [pid]);
    if (p.status !== 'on') throw bad(400, `商品「${p.name}」已下架`);
    if (p.stock < qty) throw bad(400, `商品「${p.name}」库存不足`);
    snapshot.push({ ... }); total += p.price * qty;
  }

  // ③ 扣库存（条件更新，数据库层再拦一次）
  await conn.query('UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?', [qty, id, qty]);

  // ④ 写订单主表
  await conn.query('INSERT INTO orders (...) VALUES (...)');

  // ⑤ 写订单明细（商品快照）
  await conn.query('INSERT INTO order_items (..., product_name, price, ...) VALUES (...)');

  await conn.commit();                // ⑥ 全成功才提交
} catch (e) {
  await conn.rollback();              // 任何一步失败，上面所有写操作全部撤销
  throw e;
} finally {
  conn.release();                     // 连接一定归还，否则池子会被耗尽
}
```

**为什么必须用事务**：下单要做"扣库存 + 写订单 + 写明细"三次写操作。如果不用事务，扣完库存写订单时数据库挂了，就会出现**库存少了但订单没生成**——用户的钱没花，商家的货凭空消失。事务保证这三次写"要么全成、要么全不成"。

**为什么 `finally` 里一定要 `release()`**：极端情况下不释放连接，请求多了池子里的 10 条连接全被占住，后面所有请求永久排队卡死。这是连接池最经典的事故。

**答辩话术**：事务不是"用了就安全"，而是"事务里的操作要么全对要么全错"。真正的并发安全靠的是下面的行锁。

### 知识点 8：行锁防超卖（极简版第 6 节）★★最值钱的一问

**场景**：库存只剩 1 件，两个用户同一瞬间都下单。

**不加锁会发生什么**（把这段背下来）：

```
时刻 T1：用户 A 读库存 → 1，判断够 → 准备扣
时刻 T2：用户 B 读库存 → 1，判断够 → 准备扣      ← 两个人都读到了 1
时刻 T3：用户 A 扣库存 1-1=0
时刻 T4：用户 B 扣库存 1-1=0                      ← 卖了 2 件，库存变 0，超卖 1 件
```

这就是**超卖**，根因是"读"和"写"之间有空隙，两个事务读到了同一个旧值。

**极简版的两道防线**：

```js
// 第一道：FOR UPDATE 行锁——锁住这行，别的事务想读这行必须排队等
SELECT ... FROM products WHERE id = ? FOR UPDATE

// 第二道：条件更新——就算锁漏了，数据库层也不允许扣成负数
UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?
if (!u.affectedRows) throw bad(400, '库存不足');   // 影响行数为 0 说明没扣成
```

**答辩话术（一字不差地讲）**：
> 我用的是"悲观锁 + 条件更新"双保险。`FOR UPDATE` 让并发事务串行化，第二个事务必须等第一个提交才能读到库存，读到的时候已经是 0 了，直接被 `stock < qty` 拦下。就算某些边界情况绕过了检查，`WHERE stock >= ?` 这个条件更新在数据库层面也是原子的——扣不成就是 `affectedRows = 0`，我立刻抛异常回滚。两层都过不去，就不可能超卖。

**追问：为什么不用乐观锁（version 字段）？**
乐观锁适合"冲突很少"的场景，冲突了靠重试。抢购是冲突极高的场景，重试会雪崩。悲观锁在这种场景下更直接可靠。（能说出这句，评委基本就满意了。）

### 知识点 9：订单状态机（极简版第 6 节 `POST /:id/status`）★★

```js
const flow = { pending: 0, paid: 1, shipped: 2, completed: 3, cancelled: -1 };
if (flow[status] !== flow[rows[0].status] + 1) {
  return fail(res, 400, `订单状态不允许从 ${rows[0].status} 流转到 ${status}`);
}
```

**这是把"状态流转规则"写成数据，而不是写成 20 个 if-else。**

状态图：

```
pending ──支付──> paid ──发货──> shipped ──确认收货──> completed
   │
   └──取消──> cancelled（同时回滚库存）
```

**为什么用数字编号**：编号连续，就能用 `+1` 表达"只能往前推一格"，一行代码替代"待支付能不能直接变已完成"这类分支判断。

**实测验证过的拦截**（报告里都有记录）：
- 已发货的订单点取消 → `仅待支付订单可取消`
- 已完成的订单点取消 → 同样被拒
- 已支付的订单重复支付 → `仅待支付订单可支付`
- pending 直接跳到 completed → 被状态机拦截

**答辩话术**：状态机的作用是防止数据走到不可能的状态。如果没有这层，直接调接口把订单从 pending 改成 completed，库存就永远扣着不退了，账目直接乱掉。

### 知识点 10：库存回滚 + 软删除归档（极简版第 6 节）

**库存回滚**（被"取消"和"超时取消"两处复用，所以抽成函数）：

```js
async function rollbackStock(conn, orderId) {
  const [items] = await conn.query('SELECT product_id, quantity FROM order_items WHERE order_id = ?', [orderId]);
  for (const it of items) {
    await conn.query('UPDATE products SET stock = stock + ? WHERE id = ?', [it.quantity, it.product_id]);
  }
}
```

**为什么按 `order_items` 回滚、而不是按前端传的数量**：前端能传假数据，`order_items` 是下单时写进去的真实快照，只能信数据库。

**软删除归档**：

```js
// 归档 = 打个标记，不是 DELETE
await db.query('UPDATE orders SET is_archived = 1 WHERE id = ?', [id]);
// 列表默认只查 is_archived = 0
let whereSql = 'WHERE o.is_archived = ?';   params = [onlyArchived ? 1 : 0];
```

**必答追问：为什么订单不能真删？**
订单是财务凭证，也是纠纷证据。真删了，用户说"我买过你没发货"就无从查证；而且订单被 `order_items` 引用，删了明细就成孤儿数据。所以用软删除——只在列表里隐藏，数据永远留着可追溯。

**答辩话术（顺手带出商品删除的对比）**：商品删除我做的是**拒绝**而不是软删除，因为商品被订单引用时删掉会破坏历史订单的完整性，所以返回"建议改为下架"。下架和归档本质是一样的思路：**该保留的历史数据，永远不用 DELETE**。

### 补充点 A：分页 + 动态条件拼装（极简版第 4、6 节）

```js
const where = [];                 // 条件片段数组
const params = [];                // 参数数组，与条件一一对应

if (!isAdmin) { where.push('p.status = ?'); params.push('on'); }
if (req.query.keyword) { where.push('(p.name LIKE ? OR p.description LIKE ?)'); params.push(a, a); }

const whereSql = where.length ? `WHERE ${where.join(' AND ')}` : '';
const [list] = await db.query(
  `SELECT ... FROM products p ${whereSql} ORDER BY ${SORTS[sortKey]} LIMIT ? OFFSET ?`,
  [...params, pageSize, (page - 1) * pageSize]
);
```

**两个要点**：
1. **条件动态拼、值永远参数化**。拼进 SQL 的只有 `${whereSql}` 这种纯结构片段，用户输入一律走 `?`，所以没有注入入口。
2. **排序字段必须走白名单**，这是最容易被忽略的注入点：

```js
const SORTS = { price_asc: 'p.price ASC, p.id DESC', ... };   // 只允许这 6 种
const sortKey = SORTS[req.query.sort] ? req.query.sort : 'newest';   // 不在白名单就回退默认
```

排序字段没法用 `?` 参数化（`ORDER BY ?` 会变成按常量排序），所以只能拼字符串——那就必须白名单，否则 `sort=price; DROP TABLE users--` 直接注入。

**答辩话术**：很多人以为参数化查询就彻底安全了，但 `ORDER BY` 和表名这类"结构位"是没法参数化的，必须靠白名单。这是我在写这个项目时专门处理过的一个点。

### 补充点 B：统计模块的 SQL 聚合（极简版第 7 节）

```js
const VALID = "status IN ('paid','shipped','completed')";   // 统一口径：有效订单

// 总览
SELECT COALESCE(SUM(total_amount),0) FROM orders WHERE ${VALID}
// 按天趋势
SELECT DATE(created_at) AS date, SUM(total_amount) AS amount
FROM orders WHERE ${VALID} AND created_at >= DATE_SUB(CURDATE(), INTERVAL ? DAY)
GROUP BY DATE(created_at) ORDER BY date
```

**两个细节值得讲**：
1. **口径统一**：销售额只统计有效订单（已支付/已发货/已完成），待支付和已取消不算。这个口径抽成一个常量 `VALID`，7 个统计接口全用它，保证看板上各张图能对得上账。
2. **`COALESCE(SUM(...), 0)`**：当天没有订单时 `SUM` 返回 `NULL` 而不是 0，前端图表会断线或报错，所以要用 `COALESCE` 兜成 0。

### 补充点 C：购物车持久化（极简版前端第 6 节）

```js
S.cart = JSON.parse(localStorage.getItem('simple_cart') || '[]');
function saveCart() { localStorage.setItem('simple_cart', JSON.stringify(S.cart)); }
```

工程版对应 `stores\cart.js`（Pinia store，key 是 `yunshang_cart`），本质一样：**购物车不存数据库、存浏览器本地**。

**必答追问：购物车为什么不存数据库？**
未登录用户也应该能加购物车，存数据库就得先有用户 ID。所以存本地，下单时一次性提交给后端。代价是换设备/换浏览器购物车就没了——淘宝那种跨设备同步的购物车才需要存服务端。

**追问：本地存购物车有什么风险？** 用户能手动改 localStorage 里的价格。所以下单时前端只传 `productId + quantity`，**价格一律由后端按 ID 重查**，前端传的价格完全不被信任。这就是为什么极简版下单接口的入参里根本没有价格字段。

## 五、预判追问速查（Q&A）

| 评委可能问 | 回答要点 |
| --- | --- |
| 为什么用 JWT 不用 Session | 无状态、服务端不存、横向扩容不用共享；代价是签发后无法主动作废，需黑名单补充 |
| Token 里能放密码吗 | 不能。JWT 载荷是 Base64 编码不是加密，谁都能解，只能放 id/role 这类非敏感字段 |
| 怎么防止超卖 | 事务 + `FOR UPDATE` 行锁 + `WHERE stock >= ?` 条件更新，双保险，重复了两遍 |
| 为什么不用乐观锁 | 抢购冲突极高，乐观锁靠重试会雪崩；悲观锁在这种场景更直接 |
| 事务里忘了 release 连接会怎样 | 连接池被占满，后续所有请求永久排队，服务假死。所以 `finally` 里必写 |
| 商品价格前端能不能改 | 不能。前端只传 productId 和 quantity，价格由后端按 ID 重查，前端传的价格字段直接忽略 |
| 收货人信息会不会被前端篡改 | 传 addressId 时后端回查地址簿覆盖前端传值，只有手填模式才用前端数据 |
| 订单为什么不能真删 | 财务凭证 + 被 order_items 引用，删了明细成孤儿；所以用 `is_archived` 软删除 |
| 商品为什么反而不能删 | 被订单引用的商品删了会破坏历史订单完整性，所以拒绝删除并提示"改为下架" |
| 排序参数怎么防注入 | 排序字段没法参数化，所以走白名单 `SORTS`，不在白名单就回退到默认排序 |
| 密码怎么存的 | bcrypt 加盐哈希，轮数 10，数据库不存明文；登录失败统一提示"用户名或密码错误"防账号枚举 |
| 用户名重复注册怎么处理 | 插入前先查一次，但真正保险的是数据库 `username` 字段的 UNIQUE 约束——并发下两个请求同时查都会说"不存在"，最终靠唯一索引兜底 |
| 订单超时怎么自动取消 | 服务内 60 秒定时扫描，`created_at` 超过 30 分钟的 pending 单事务内取消并回滚库存；另有管理员手动触发接口用于演示 |
| 并发下单同一订单重复支付怎么办 | 支付用 `FOR UPDATE` 锁住订单行，改状态带 `WHERE status='pending'`，第二次进来状态已变，`affectedRows=0` 被拦 |
| 为什么用连接池不用单连接 | 建连接要握手+认证，几十毫秒；池子预先建好 10 条常驻复用，避免每次请求重连把数据库打满 |
| 为什么 `dateStrings: true` | MySQL 驱动默认把 DATETIME 转 Date 对象，序列化后变 ISO 带时区字符串，前端还得再转；直接返回字符串省掉整套时区坑 |
| 极简版缺了什么 | 少的是分层、抽象、错误处理中间件——不产生功能，只产生可维护性。功能上 37 个接口一个不少，同一套 54 项测试全过 |
| 项目还有哪些没做 | 真实支付渠道、商品评价、优惠券、多规格 SKU、退款售后、图片上传、订单导出。不是做不了，是实训阶段在"闭环完整"和"每个模块讲得透"之间做的取舍 |
